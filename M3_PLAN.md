# M3 native Windows implementation plan

Scope: official Tauri v2 notification, single-instance, and autostart plugins; native tray/window lifecycle; a minimal real break window; native settings and diagnostics. Preserve the Rust scheduler and offline boundaries. No history analytics, expanded onboarding/settings workflows, updater, or M4 redesign.

1. `src-tauri/Cargo.toml`, `lib.rs`, `tauri.conf.json`: enable Tauri tray support, register single-instance first (before storage/scheduler), notification and opt-in autostart plugins. Add a predefined hidden `break` window. Hide main on close only if the tray is available; explicit Quit exits all windows/processes. Startup-launched instances start hidden only when the tray is ready. Repeated manual launches show the existing main window and never start another scheduler.
2. `native/model.rs`, `native/notifications.rs`, `native/startup.rs`: typed native status and diagnostics. Notifications are created in Rust after scheduler commit. Do not register toast action types/buttons or OS notification schedules. Where the installed plugin supports toast-body click, validate its reminder UUID against current Rust state before opening the break window; stale notifications cannot act on later reminders.
3. Diagnostics read only this application's Windows toast setting and the documented shell notification-attention hint where available. Distinguish disabled-in-app, denied by Windows/policy, submission accepted but display unconfirmed, and preparation failure. Do not claim to fully detect DND/Focus Assist or infer delivery from plugin success. Respect suppression; never force a break window into focus for automatic reminders. Explicit user tray/click actions may show/focus the requested window.
4. Persist native preferences through the existing worker-owned settings transaction, with backward-compatible defaults: notifications on, autostart off. Only dedicated commands may change native fields. Autostart changes require an explicit user command; reconcile/show actual OS registration without silently enabling at boot. Roll back the OS change if preference persistence fails. No frontend plugin mutation grants.
5. `native/tray.rs`, `native/windows.rs`: Show, Open current break, Take eye/movement break, Pause 30m/1h/2h, Resume, Settings, Quit. All scheduler actions run through its serialized handle off the GUI thread. Update tray state/tooltip from committed snapshots. Keep main usable if tray setup fails. Break close/Esc hides without recording completion; unanswered timeout remains Rust-owned.
6. `commands.rs`, `build.rs`, capability files: main gets only needed native commands and existing scheduler permissions. Break gets read state/start/outcome/hide commands and listen/unlisten, without settings mutation, autostart, Quit, filesystem, shell, HTTP, or broad notification APIs. Emit committed state to both trusted windows.
7. Existing React shell plus `BreakPanel.tsx`, native API/types/hook/settings component: accessible real Start/Done/Snooze/Skip, pending/error handling, focus/keyboard/Esc behavior; opt-in autostart toggle, notification toggle, test reminder and diagnostics. Continue using existing design system. No JS reminder timer or fake countdown.

Verification: Rust tests for native policy, preference compatibility/authorization, stale-click matching, rollback, and scheduler regressions; frontend tests for break actions, stale/error states, native toggles and failures; lint/types/build/browser regressions. Build NSIS, install per-user in a reviewed local path, launch the installed executable, test notification submission plus actual Windows toast evidence when observable, tray/close/Quit, single instance, and autostart opt-in/off. Restore changed QA preferences/registration; preserve history. Record tests that cannot be observed (especially visible banner/click, DND/denial, clean Windows 10/11, and actual login) as pending, never as passed.
